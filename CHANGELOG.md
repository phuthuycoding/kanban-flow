Follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions follow SemVer; the `0.x` line is the TypeScript rewrite (the older `v1.x`/`v2.x` tags belong to the shell installer).

## [Unreleased]

### Added
- **`kf doctor [--json]`.** A diagnosis at the project level, filling the gap between `kf validate` (work items only) and `kf autoconfig` (setup progress only, always exits 0). It checks the stage directories, that the config parses, each work item's metadata, whether the skills are still installed, and config fields that no longer mean what their names suggest. Read-only, does not stop at the first problem, exits 1 on any ERROR. It works **even when `.kf/config.json` is broken** — which is exactly when it is needed. Work items that are not yet valid are counted but never change the verdict: that is the normal state of a pipeline in motion.
- **Four more formats in the secret scanner**: three-segment JWTs (`eyJ…`), Slack webhooks, Discord webhooks, and connection strings carrying a password (`scheme://user:<password>@host`). These are the shapes most likely to land in an artifact — a token pasted from a real request, a webhook URL pasted while describing an integration, a DSN pasted while reproducing a database bug — and all of them used to pass silently. Zero false positives across every real artifact in this repository, with a test that holds the line. The classification rule is now written down in the code: a pattern is high-confidence if and only if it carries a **prefix only a real credential has**; a connection string does not qualify, because an honest template has the same shape.
- **Declared contexts.** `.kf/config.json` accepts `contexts`, and **the first entry is the default** — there is no second field to drift out of step with the list, so no configuration exists whose default its own guard would reject. `defaultContext` is kept for reading older projects and is ignored once `contexts` is set.
- `kf new` refuses a context that is not on the list and names the nearest match. A name differing only in case is refused too, because accepting `Auth` next to `auth` is exactly how a second docs tree appears on a case-sensitive filesystem.
- `kf contexts [--json]`: lists the declared contexts with a work-item count each, flags contexts in use but not declared, and prints a survey brief for an agent when nothing is declared. Read-only; it never writes.
- `kf init` folds the context question into a single prompt that accepts a list, without adding a new question. Re-running `kf init` on a project that has a config but no `contexts` does **not** add the field: upgrading the tool must never start rejecting contexts the project already uses.
- `kf autoconfig` adds a checklist line for `contexts`, and takes the default context from the same source as `kf new` instead of reading `defaultContext` directly.
- **A role-based multi-agent harness.** The `harness` block in `.kf/config.json` has three layers, `stage → role → runner`: `roles` maps a role (writer, coder, tester…) to a runner, with a `brief` injected into the prompt and an `output` file the role must write; `stages` assigns one role or a **chain of roles run in order** to each stage; `runners` holds each CLI/model's argv template plus how to capture a session and read usage. Changing the model for one role is a one-line edit, and the stage is untouched.
- `kf run <feature>` runs the current stage's role chain as headless workers (blocking, or `--detach` with a supervisor), with `--role` for a single role, plus `--fresh`, `--timeout`, `--dry-run`. A role that does not finish with `DONE` stops the chain, and the later roles do not run.
- Sessions are kept per **work item and role** (`.kfw.json.sessions`), so a repair loop resumes the right session and two roles sharing one CLI never see each other's context. `runs[]` records the role, the runner, the position in the chain, the exit code, the `STATUS:` line, and usage when the CLI reports it.
- `kf runs` lists runs with chain progress and marks `chain stopped i/n` when a chain ended early; `kf harness` prints the three layers and which runners have a CLI on PATH; `kf status` prints the assigned roles; `kf view` aggregates `metrics.runs.byRole` and usage per role.
- Runner presets for claude, codex, devin (exercised for real on 2026-09-19), gemini and opencode; `kf init` seeds six roles — architect, researcher, writer, coder, tester, reviewer. Documented in `docs/workflow/harness.md`.
- **The `cancelled` stage and `kf cancel`.** A second way out for a work item: stop it for good with a mandatory `--reason`, store `cancellation { at, by, reason, fromStage }` in `.kfw.json`, and reopen with `kf stage <feature> <fromStage>`. The stage sits off the linear axis (`STAGE_INDEX = -1`), so no artifact, approval or report is demanded of it; in exchange, a missing reason is `cancellation_missing`. It refuses while a worker run is live, runs the `cancelled.sh` hook, lists the canonical docs of an archived item, and deletes them only with `--purge-docs` plus confirmation. `kf view` and the dashboard count them separately and leave cancelled items out of the `completionRate` denominator.
- Vitest `globalSetup` builds `dist/` before the suite runs (the detach tests need a real CLI).
- `LICENSE` (MIT) at the root, and publish metadata in `package.json`: `author`, `repository`, `homepage`, `bugs`, `keywords`, `publishConfig.access`.

### Fixed
- **`kf status` hid the thing that was actually blocking.** It only walked the artifact list, so an item could print `Artifacts: 5/5` and `Next: … kf approve`, and `kf approve` would then fail on four traceability findings status had never looked at. Worst of all for automated runs: the harness prompt tells **every** worker to run `kf status` for its checklist. Status now carries the blocking findings straight from `validateFeature` — no rule is restated — and no longer suggests a command that is about to be refused.
- **A secret inside a cancelled item's artifact was never reported.** The secret scan lived inside the "artifact is due" loop, and `STAGE_INDEX = -1` made that loop skip everything — so **cancelling an item was the quietest way to take a committed token off the radar** while leaving it in the repository. `checkSecrets` is now its own check, running over **every artifact on disk, at every stage**, `cancelled` included. That also closed a wider hole: a secret in a not-yet-due artifact of a live item was equally silent.
- **Reopening a cancelled item into `planning` was refused while `kf validate` called it valid.** `kf stage` validated the move to `planning` as if the item were in `brainstorm`, which walked past the shortcut for `cancelled` and re-raised `requirement_unconfirmed` — then printed a report blaming a stage the item was not in. The only way through was `--force`, meaning a permanent bypass record had to be stamped to pass a gate that should never have held. The exemption now applies to `cancelled` only; a live item returning to `planning` is still held to the `brainstorm` gate as before.
- **`listFeatures` died on a dangling symlink under `.works/`.** An unguarded `statSync` made `kf list`, `kf contexts`, `kf new` and `kf view` all throw a raw `ENOENT` — including `kf list`, the command you run to find out what is wrong. A broken entry now surfaces as an invalid item instead of vanishing, and any error other than "target does not exist" still propagates.
- **An item cancelled out of `brainstorm` could never validate.** The `requirement_unconfirmed` check sat outside the gate loop with no stage guard, so it fired on `cancelled` too — and cancelling from `brainstorm` is exactly when the requirement is still `pending`. The result: `kf validate --all` failed forever in CI, and **the reopen command `kf cancel` itself prints was refused**. A cancelled item is now asked for exactly two things — the cancellation reason, and the bypass trail if there is one — and the requirement check is scoped to the stages that actually owe it.
- Reopening an item cancelled from `dones` used to be a **permanent dead end**: `kf stage <x> dones` routed to archive, and archive refuses a cancelled item before it ever looks at `--force`. Reopening now puts the item back where it was: `status: "archived"` is restored and the canonical docs are re-synced by archive, since `--purge-docs` may have deleted them.
- `requirement_unconfirmed` no longer misfires at `dones`, `review` and `backlog` with the wording "before leaving brainstorm", while keeping full strictness at `planning`, where `kf approve` validates.

### Changed
- **Package renamed `kaban-flow` → `kanban-flow`**, version `0.3.0`. The binary is still `kf`, and the data directories are still `.kf/` and `.works/`. Uninstall with `npm rm -g kanban-flow`.
- **GitHub repository renamed** to `phuthuycoding/kanban-flow` to match the package name; `repository`, `homepage` and `bugs` in `package.json` were updated to match.
- **The entire user-facing surface moved to English**: `PHASE_NAMES` for `backlog`/`cancelled`, the dashboard's context and approval labels, the whole dashboard HTML (`lang="en"`), the `kanban-bug`/`kanban-brainstorm`/`kanban-plan` skills, the `phase-2-use-case-specification.md` template, `README.md`, `docs/README.md`, `kanban-flow/README.md` and nine files under `docs/workflow/`.
- **README rewritten**: it opens with the problem (an agent reporting tests it never ran) before the mechanism, installs in one line, and states its differences honestly against a market survey — claiming no exclusivity over mechanics others already implement, only the execution id and the combination.
- **`kanban-review` now reviews bugs adversarially.** Every bug review states two things, and "none" counts only when it says what was examined: *reachable regressions* (what else calls the changed code; a guard added for one entry point rarely covers the rest) and *disproved claims* (the reviewer re-runs the reproduction rather than trusting the report, and verifies any comment carrying the argument for the fix). Plus a new rule: a passing test does **not** prove it would fail without the fix — remove or invert the predicate and confirm a test goes red; if none does, that is itself a finding. `kanban-bug` was updated to match, listing sibling entry points at triage time.
- `files` in `package.json` is narrowed to `docs/workflow`, so 35 internal canonical docs (~220KB) no longer ship in the npm package.
- The dashboard renders times in the browser's locale instead of a hardcoded `vi-VN`.

## [0.2.0] - 2026-09-19

### Added
- `.kfw.json` records `bypasses[]` whenever `--force`/`--skip-hooks` genuinely skipped a gate or a hook; `kf validate` warns with `gate_bypassed`, `kf status` prints `Bypasses:`, and `kf view --json` and the dashboard expose `metrics.bypassed`.
- Validator error `testing_exit_code`: a `PASS` testing report must have a Commands and Evidence table with at least one command and every exit code `0`.
- `kf init` seeds `AGENTS.md` (commands from the manifest plus workflow conventions); it never overwrites an existing `AGENTS.md`/`CLAUDE.md`.
- GitHub Actions CI: typecheck, lint and test on Node 20 and 22.
- `CHANGELOG.md`.

### Changed
- `kf autoconfig` generates its Workflow guide section from the parser's own help strings (the previous hand-written text printed the wrong syntax for `kf stage --to`, `kf approve --change` and `kf new <context> <name>`); it prefers `stacks` in `.kf/config.json` over auto-detection.
- Secret scan: the placeholder exemption applies to the captured value only, not to the whole line; the high-confidence group (`ghp_`, `sk-`, `AKIA`, `xox*-`, PRIVATE KEY) is excused only when the value itself is masked (`xxxx`/`****`). Reported hits have the value masked.
- `npm run typecheck` covers `src/tests/**`; the build uses `tsconfig.build.json`, so `dist/` is unchanged.
- `src/workflow/validate.ts` split into `findings`, `secrets`, `validate-artifacts`, `validate-approval`, `validate-reports`, `validate-traceability` and `direction`; import paths and the API are unchanged.
- The help strings for `kf status`, `kf instruct` and `kf validate` now carry descriptions.
- README: notes that `.sh` hooks need `bash` (on Windows: WSL or Git Bash), and reminds you to run `npm run build` after `git pull`.

### Unreleased on `main` before this version
- Project-only skills, `kf install`/`uninstall --purge`, `kf autoconfig`, monorepo stack detection plus `kf rules`, the `artifact_secret` secret scan, the AI-risk lens in kanban-review, and placeholder detection that skips code spans.
